Imports and File Structure

Importing

Section titled “Importing”

An import names either a single .sau file or a folder module (a directory with an init.sau — see Folder Modules), and the path is relative to the importing file’s directory, then the project’s src_dirs. The module comes first, so an editor knows what it can offer before you type a name.

Or import the module as a whole. Everything it exports comes in, as with from shine import *, and is also reachable through its name:

An import brings in only what that module exports.

The qualified name is there for when two modules export the same one. A namespace is named after the last part of its path. A path whose last part is not a name, like "my-lib", needs as. shine.Window works anywhere a name or a type does, and a name the module does not export is reported as one: "`shine` has no export named `Windw`".

Apps and Libraries

Section titled “Apps and Libraries”

A project is one of two shapes, declared by kind: in saule.config:

kind Has entry: saule run Purpose
"app" (default) yes runs it a program
"library" no refuses, and says why imported by other projects

Scaffold either with saule init:

A library’s src/init.sau is its public surface — whatever that file exports is what importers see. Running one is a category error and reports as such rather than failing on a missing entry file.

Importing from a Dependency

Section titled “Importing from a Dependency”

A project listed in dependencies: is reachable by its name:. Naming the dependency on its own imports the package itself:

A package exposes itself through an init.sau in one of its src_dirs — the same folder module rule that applies anywhere else, so there is one convention to learn rather than a special case for dependencies. A package without one can still have its modules imported by path, but its name alone won’t resolve.

Folder Modules (init.sau)

Section titled “Folder Modules (init.sau)”

A folder becomes a single importable module by giving it an init.sau. Importing the folder imports that file, so whatever it exports is the folder’s public surface.

Re-exports

Section titled “Re-exports”

export from passes names on: they are imported here and exported again, so a folder of files can be consumed as one unit.

Consumers then import the folder itself and get everything it passes on:

Only what is written with export from is passed on. A plain from … import keeps its names private to the file, in an init.sau too, so a file’s imports stay an implementation detail. Any file can re-export, and a re-export of a re-export works. A namespace cannot be re-exported; name what to pass on instead.

Exporting

Section titled “Exporting”

Add export before a class, interface, enum, function, or variable to make it accessible from other files:

An export name: T = value is a module variable (see Variables) — a single value shared by every file that imports it, not a copy per importer.

A file without export is private to itself — even sibling files in the same folder can’t see its declarations. The only way to share code across files is to export it and import it explicitly.
